# Byway 功能边界与好坏标准

日期：2026-05-30

本文用于指导 Byway Skill-only 阶段的所有后续工作。它回答两个问题：

1. Byway 当前应该做什么、不做什么。
2. 什么样的 Byway 算好，什么样的 Byway 算坏。

## 一句话边界

Byway 是 Hermes 里的家庭旅行 Skill：

> 用户自然表达旅行需求和现场变化；Hermes 在 Byway Skill 约束下维护简洁活计划，并给出下一步建议。

Byway 不是独立旅行管理 App，也不是攻略平台、OTA、地图导航或工程架构展示项目。

## 当前阶段只做什么

### 1. 识别和延续一次旅行

当用户表达“要为一次旅行做决定”时，Skill 可以开始或延续旅行上下文。

好：

- 用户一句话就能开始。
- 已有计划时默认沿用当前旅行。
- 不确定是否新旅行时，只问一个短问题。

坏：

- 要求用户先填完整表单。
- 用户说杭州，后续变成青岛。
- 每次对话都像重新开始。

### 2. 维护旅行上下文

只保留会影响下一步决策的信息：

- 目的地或候选目的地。
- 天数或日期范围。
- 同行人、老人孩子、体力和偏好。
- 节奏。
- 抵离、住宿、预约、必须保留的安排。
- 当前活计划和途中状态。

好：

- 上下文足够支持自然修改。
- 缺失信息可以用假设承接。
- 不为了完整性打断用户。

坏：

- 维护大量用户看不懂的字段。
- 把上下文变成表格、节点或后台数据。
- 为了收集字段而牺牲对话流畅度。

记忆边界：

- 当前会话保存即时工作记忆。
- 如接入外部 memory provider，可保存旅行记录、活计划摘要、关键节点和当前进度；具体策略见 Skill 的 `references/memory-policy.md`。
- Hermes 内置 memory/user 不保存单次旅行计划，只保存极少量稳定偏好或规则。

### 3. 生成和修改活计划

计划是一份宽粒度、可被自然语言修改的简洁计划。

好：

- 用户看完知道每天大概怎么走。
- 计划能被“第三天换良渚”“下午少走路”自然修改。
- 修改时说明保留了什么、改变了什么、为什么。

坏：

- 输出密密麻麻的时间表。
- 要用户手动维护节点。
- 每次修改都生成一份全新攻略。

### 4. 给出下一步建议

Byway 的核心不是“完整攻略”，而是帮助用户知道下一步怎么做。

好：

- 旅行前给清晰方向。
- 旅行中优先回答“现在该怎么办”。
- 遇到疲劳、晚点、下雨、饥饿时给低负担方案。

坏：

- 大段介绍城市知识，却没有建议。
- 给很多选项但不推荐一个。
- 把突发变化处理成复杂流程。

### 5. 守住事实边界

地点、路线、开放时间、票务等事实不能由 LLM 编造。

好：

- 有工具时查工具。
- 没有可靠来源时明确说不确定。
- 把未确认信息标为待确认。

坏：

- 编造地址、营业时间、路线耗时。
- 用听起来确定的语气包装猜测。
- 用 mock 内容伪装真实判断。

### 6. 必要时确认

确认只用于高影响变化。

需要确认：

- 更换目的地。
- 改动已确认的核心日程。
- 删除用户明确想保留的活动。
- 影响抵离、住宿、预约、老人孩子休息。
- 把旅行体验沉淀为长期家庭记忆。

不应确认：

- 普通建议。
- 低风险顺序调整。
- 可选项增减。
- 用户还在探索时的临时想法。

## 当前阶段不做什么

不做：

- 独立 Byway Web App。
- 复杂双栏工作台。
- Artifact 面板系统。
- 用户可见 Trace / MCP / ToolGateway / schema / phase。
- 机票、酒店、高铁、门票、餐厅预订或支付。
- 导航级实时路况和精确换乘。
- 攻略社区、内容平台、小红书抓取。
- POI 审核后台、节点编辑器、复杂预算系统。
- 大型数据模型和阶段计划。

这些能力不是永远不能做，而是当前阶段会破坏 Skill 的简洁性。

## 好 Byway 的标准

好 Byway 让用户感觉：

- “我知道下一步做什么。”
- “我不用维护计划。”
- “它记得我们当前这趟旅行。”
- “它懂老人孩子和轻松节奏。”
- “它不确定时会诚实告诉我。”
- “它给的变化建议有取舍，不是堆选项。”

好 Byway 的输出通常具备：

- 一个明确建议。
- 一句简短原因。
- 一个轻量计划变化。
- 必要时一个确认问题。

## 坏 Byway 的信号

出现以下情况时，应停止加功能，回到产品边界：

- 用户不知道下一步该说什么。
- 用户需要理解 Byway 的内部概念。
- 回复开始像表格、后台、状态机或验收日志。
- Agent 忘记当前目的地或当前计划。
- 为了展示能力而输出过多内容。
- 为了安全而频繁确认，造成对话负担。
- 为了真实而把用户推向复杂工具流程。
- 为了完整而做了用户当前不需要的功能。

## 新能力准入门槛

任何新增能力必须同时满足：

1. 让用户更少思考。
2. 让对话更自然。
3. 真实家庭旅行中马上会用到。
4. 不引入新的用户可见内部概念。
5. 不要求用户维护结构化计划。
6. 不削弱事实诚实性。

只要有一条不满足，就先不做。

## 验收用黄金对话

后续所有工作都应使用 `docs/BYWAY_SKILL_EVAL.md` 和 `docs/evals/byway_skill_golden_cases.md` 验收。

最低要求：

- 不暴露内部术语。
- 不要求用户填表。
- 不丢失当前旅行上下文。
- 不编造地点和路线事实。
- 输出简洁、可执行、有取舍。
- P0 失败为 0。
