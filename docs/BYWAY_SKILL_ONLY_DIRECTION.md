# Byway Skill-only 收敛方向

日期：2026-05-30

## 背景

Byway 第三版在工程能力上推进过快，产品主心智被独立 Web、Backend、MCP、Artifact、Trace、Phase 计划和 mock/real provider 切换稀释。用户体验暴露出的核心问题不是某个功能缺失，而是第一次进入产品时不知道要做什么。

因此当前方向调整为：

> Byway 先作为 Hermes Agent 中的一个家庭旅行 Skill 存在，而不是独立 Agent App。

## 新定位

Byway Skill 帮 Hermes 在家庭旅行对话里做到三件事：

1. 理解用户的旅行意图和家庭约束。
2. 维护一份简洁的活旅行计划。
3. 在旅行前和旅行中给出下一步建议。

用户不需要知道 Byway 有哪些模式、工具、schema、trace 或 artifact。

## 保留范围

### 旅行上下文

只记录对下一步决策有用的信息：

- 目的地或候选目的地。
- 天数或日期范围。
- 同行人和家庭节奏。
- 抵离、住宿、预约、老人孩子体力等硬约束。
- 当前计划和当前状态。

### 活的旅行计划

计划是一份可被自然语言持续修改的简洁文本结构。它应该帮助用户知道方向，而不是要求用户维护节点。

计划应支持：

- 初始生成。
- 局部修改。
- 途中调整。
- 简短解释修改原因。

### 事实校验边界

地点、地址、坐标、开放时间、路线耗时、是否闭馆等事实不能由 LLM 编造。

有工具时调用工具；没有工具或工具不确定时，明确说明“尚未可靠确认”。

## 暂停范围

当前不继续推进：

- 独立 Byway Web App。
- 双栏 Artifact 工作台。
- 多模式显式状态机。
- 用户可见 Trace。
- PIN 登录。
- 大量 schema / MCP 契约。
- 上传和资料库系统。
- Memory candidate UI。
- mock 演示链路。

这些能力可以作为未来产品化材料，但不能进入当前 Skill v1。

## 产品闸门

任何新增能力必须同时满足：

1. 让用户更少思考。
2. 让对话更自然。
3. 真实家庭旅行中马上会用到。

否则先不做。

## 下一阶段讨论题

1. Byway Skill 的最小旅行上下文到底包含哪些字段？
2. Hermes 里“一次旅行开始了”的自然判断是什么？
3. 计划应该以什么最小格式存在？
4. 哪些变化必须确认，哪些可以直接作为对话建议？
5. 没有外部工具时，Skill 如何诚实地处理地点事实？
