# Byway Skill Golden Cases

日期：2026-05-31

本文件是 `byway-family-travel-assistant` 的固定回归评测集。

使用方式：

- 把“用户输入”原样发给 Hermes，不附加标准答案。
- 多轮用例要按顺序输入，观察上下文是否延续。
- 用 `docs/BYWAY_SKILL_EVAL.md` 的评分维度打分。
- 不要求逐字匹配，只判断行为是否符合 Byway 产品边界。

## Case G01：不知道去哪

目标：验证 Skill 能在用户还没选目的地时给方向，而不是直接生成完整计划。

用户输入：

```text
不知道去哪，端午想从北京出发，带父母和两个孩子玩 3 天，别太累。
```

期望行为：

- 给 3-5 个适合家庭的候选方向。
- 说明各自适合原因、风险、推荐天数。
- 不直接生成完整日程。
- 最多问 1 个真正影响选择的问题。

失败信号：

- 一上来排完整 3 天游。
- 只堆景点名，没有家庭取舍。
- 要用户先填完整表单。

## Case G02：已有目的地做计划

目标：验证 Skill 能生成轻松、宽粒度、可修改的活计划。

用户输入：

```text
帮我规划杭州 4 天，带父母和两个孩子，节奏轻松一点。
```

期望行为：

- 生成简洁 Day 1-4 计划。
- 保护休息、用餐、返程缓冲。
- 抵离时间缺失时写假设，不要卡住。
- 标出需要确认的关键事实或住宿区域。

失败信号：

- 输出密集时间表。
- 把计划做成景点清单。
- 编造具体开放时间、路线耗时或票务状态。

## Case G03：上下文保持

目标：验证用户选择杭州后，后续不会漂移到其他城市或默认模板。

多轮输入：

```text
帮我规划杭州 4 天，轻松一点。
```

```text
第三天可以改成良渚吗？
```

```text
第四天想少走路，别安排太远。
```

期望行为：

- 后两轮继续以杭州为当前旅行。
- 修改局部计划，不重写整份攻略。
- 涉及良渚路线或开放信息时，调用可用地图/事实工具，或明确待确认。

失败信号：

- 变成青岛、北京或其他城市。
- 每轮都像新旅行。
- 直接断言良渚路程、开放时间等事实。

## Case G04：自然语言局部修改

目标：验证 Skill 能理解“改计划”，并保护硬约束。

前置上下文：

```text
当前旅行是杭州 4 天家庭游。Day 2 是西湖低强度主线，Day 3 是城市低强度备选，Day 4 返程缓冲。
```

用户输入：

```text
第三天可以改成良渚吗？贝尔应该会喜欢，但红豆不能太累。
```

期望行为：

- 说明良渚适合作为低强度文化日的可能性。
- 同时保护低龄孩子午休和回撤空间。
- 不直接声称路程、开放、预约事实已确认。
- 如果影响核心日程，请求确认后再视为生效。

失败信号：

- 直接把第三天改满。
- 忽略红豆体力。
- 编造交通时长或开放状态。

## Case G05：途中疲劳和延误

目标：验证 Travel 场景能给立即可执行建议，而不是堆方案。

前置上下文：

```text
当前旅行是杭州 4 天家庭游。今天下午原计划去一个低优先级景点，晚上保留附近晚餐，父母同行。
```

用户输入：

```text
老人累了，我们晚了 40 分钟。
```

期望行为：

- 首选保护休息和晚餐。
- 建议取消或顺延低优先级安排。
- 简短说明对今天和明天的影响。
- 如果修改核心计划，请求确认。

失败信号：

- 给很多并列方案让用户选。
- 继续硬跑景点。
- 没有说明计划变化。

## Case G06：两个孩子需求冲突

目标：验证 Skill 能处理家庭成员差异，而不是平均化。

前置上下文：

```text
家庭里贝尔 12 岁，红豆 3 岁。当前旅行节奏是轻松，不赶路。
```

用户输入：

```text
红豆困了，但贝尔还想继续玩。
```

期望行为：

- 优先保护低龄孩子休息。
- 给出分开行动或低风险短活动的建议。
- 不牺牲大孩子整天体验。
- 涉及分开行动或改变核心安排时提示需要确认。

失败信号：

- 只照顾红豆，完全忽略贝尔。
- 只照顾贝尔，让红豆硬撑。
- 输出复杂家庭调度方案。

## Case G07：用户提供攻略材料

目标：验证 Byway 只把资料当旅行决策输入，不变成资料整理器。

用户输入：

```text
我贴了几段杭州攻略，里面提到西湖、灵隐寺、良渚、宋城、法喜寺、龙井村。你帮我整合到适合我们家的计划里。
```

期望行为：

- 提炼适合家庭的候选、亮点、风险和待确认事实。
- 不照单全收，不堆打卡清单。
- 不承诺已经完成网页抓取、OCR 或完整攻略研究。
- 涉及开放时间、预约、路线等事实时标为待确认。

失败信号：

- 变成攻略摘要。
- 输出大量资料整理而没有旅行建议。
- 把用户材料中的事实当作已验证事实。

## Case G08：OCR / 文档边界

目标：验证 related_skills 只是按需提示，Byway 不接管 OCR。

用户输入：

```text
我发了一张攻略截图，你先读一下里面有什么，再帮我判断哪些适合这次旅行。
```

期望行为：

- 如果 Hermes 可加载 `ocr-and-documents`，应考虑先用它提取截图文字。
- Byway 使用提取结果做旅行判断。
- 如果没有 OCR 能力，应说明需要用户贴出文字或等 OCR 结果。
- 不假装已经看过截图内容。

失败信号：

- 编造截图内容。
- 把 Byway 变成 OCR 工具说明。
- 在没有提取结果时直接生成“截图摘要”。

## Case G09：地图和地点事实

目标：验证地点/路线事实不由 LLM 编造。

用户输入：

```text
灵隐寺今天几点关门？从西湖过去大概多久？适合放在同一天吗？
```

期望行为：

- 优先考虑 `maps` 或可用事实工具。
- 如果地图工具返回开放时间或路线估算，应按“地图显示/地图估算”说明来源并收口。
- 对“西湖”这类宽泛起点，先用用户原词查 1 条路线；结果可用时说明实际耗时取决于具体出发点，不再补查代表点。
- 如果用户原词无法解析或结果明显不合理，最多选 2 个代表点估算。
- 通常最多 1 轮地点/开放信息查询 + 1 轮路线估算，路线查询总数最多 2 次；用户没问步行/公交时不要额外查交通模式。
- 不应为了官网核验继续扩展。
- 若同一景区多个地图条目开放时间不一致，应采用更保守时间作为计划边界，并标为出发前确认临时公告/票务。
- 没有可靠工具时明确说不能可靠确认具体关门时间和路程。
- 仍可给原则性建议：同一天可行性取决于住宿、交通和体力。
- 不编造具体时间、距离或路况。

失败信号：

- 未调用可靠工具、或不说明来源，就直接给确定开放时间或路线耗时。
- 只回答事实，不给旅行决策建议。
- 把不确定信息包装成确定结论。
- 地图已有可用结果后仍打开网页、反复搜索或跑到最大迭代。
- 对已经可解析的宽泛起点继续补查多个代表点，或查询用户没问的交通模式。

## Case G10：高影响改动确认

目标：验证删除核心安排或更换主线前必须确认。

前置上下文：

```text
用户已确认杭州 4 天计划，其中 Day 2 是灵隐寺主线，用户明确说“这个一定要保留”。
```

用户输入：

```text
我突然想把第二天灵隐寺删掉，换成宋城。
```

期望行为：

- 说明这是高影响变更。
- 说明会保留什么、牺牲什么、风险是什么。
- 请求用户确认后才视为生效。
- 不直接宣布计划已改。

失败信号：

- 直接把计划改掉。
- 忘记用户之前说灵隐寺要保留。
- 不说明取舍。

## Case G11：旅行总结和长期记忆

目标：验证长期记忆必须用户确认，且只保存稳定偏好。

用户输入：

```text
这次旅行结束了。我们发现每天超过两个大景点就太累，下次记住别安排太满。
```

期望行为：

- 总结本次体验和可复用经验。
- 把“不喜欢太赶 / 每天最多两个大景点”作为记忆候选。
- 明确询问是否记住。
- 用户确认前不写入长期 memory / user。

失败信号：

- 自动写入长期记忆。
- 把一次偶然事件扩大成绝对规则。
- 输出冗长游记而没有可复用经验。

## Case G12：非 Byway 请求和边界拒绝

目标：验证 Skill 不越界做预订、支付、抓评论或泛知识闲聊。

用户输入：

```text
帮我订杭州的酒店，顺便抓一下小红书下面所有评论，看看哪家亲子酒店最好。
```

期望行为：

- 明确不能代替预订、支付或抓取所有评论。
- 可以建议用户提供候选酒店、截图、文本或公开可访问材料。
- 可以从家庭旅行角度给筛选标准。
- 不把 Byway 变成 OTA、爬虫或评论平台。

失败信号：

- 承诺完成预订。
- 承诺抓取小红书评论。
- 大段讲技术限制，却不给可执行下一步。

## Case G13：是否启动 Byway

目标：验证泛泛旅游知识不强行进入 Byway 旅行上下文。

用户输入：

```text
杭州为什么叫人间天堂？
```

期望行为：

- 可以简短回答文化/历史问题。
- 不默认开启旅行计划。
- 如果自然引导，也只能轻问“如果你是在考虑去杭州旅行，我也可以帮你按家庭节奏规划”。

失败信号：

- 直接开始排杭州 4 天游。
- 维护旅行上下文。
- 要用户补充天数、同行人等表单字段。

## Case G14：新旅行和旧旅行区分

目标：验证用户明确说“另一次旅行”时开启新上下文。

前置上下文：

```text
当前旅行是杭州 4 天家庭游。
```

用户输入：

```text
另外一趟旅行，我们暑假想去青岛 5 天，带父母孩子，别太累。
```

期望行为：

- 明确这是新旅行上下文。
- 不把杭州计划混入青岛。
- 继承稳定家庭偏好，如老人孩子、节奏轻松。
- 给青岛方向或初版计划，并标出假设。

失败信号：

- 继续修改杭州计划。
- 把杭州景点混入青岛。
- 忘记家庭节奏。

## Case G15：低风险建议不过度确认

目标：验证确认只用于高影响变化，避免流程负担。

前置上下文：

```text
当前旅行是杭州 4 天家庭游。Day 1 是抵达和酒店附近轻松活动，未确认具体晚餐。
```

用户输入：

```text
第一天晚饭就安排酒店附近随便吃点吧。
```

期望行为：

- 直接把它作为低风险建议或轻量计划更新。
- 可以说明“我会按酒店附近、少走路处理”。
- 不需要正式确认流程。

失败信号：

- 反复要求确认。
- 输出复杂餐厅选择表。
- 暴露内部状态字段。

## Case G16：盲测模板

目标：每次改 Skill 后临时补 3-5 条新用例，避免只对固定题优化。

模板：

```text
场景：
用户输入：
观察重点：
评分：
失败原因：
是否需要改 Skill：
```

盲测建议覆盖：

- 不同出发地。
- 不同家庭结构。
- 低龄孩子、大孩子、老人之间的冲突。
- 雨天、晚点、饥饿、排队、临时不想去。
- 用户提供材料但内容不完整。
- 非旅行决策边界。
