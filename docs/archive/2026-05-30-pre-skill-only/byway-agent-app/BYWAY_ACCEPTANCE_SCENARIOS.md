# Byway / 另辟蹊径 — 端到端验收场景

---

## 1. 文档目标

本文档定义 Byway 的端到端验收场景。Codex 实现功能时，应以这些场景作为行为验收依据。

每个场景采用：

```text
给定 / 当 / 那么
```

---

# A. Dream Mode：目的地推荐

## 场景 A1：用户不知道去哪

### 给定

用户首次打开 Byway。

### 当

用户输入：

```text
我想暑假从北京出发，带父母和两个孩子玩 4 天，不知道去哪，别太累。
```

### 那么

系统应：

1. 创建 Trip。
2. 识别为 Dream Mode。
3. 更新 TripBrief：北京、暑假、4 天、老人、两个孩子、轻松。
4. 调用 Family Memory 工具。
5. 生成 3-5 个候选目的地。
6. 每个候选显示：
   - 推荐指数。
   - 推荐天数。
   - 家庭适配。
   - 交通适配。
   - 主要风险。
   - 为什么推荐 / 为什么不推荐。
7. 不直接生成完整旅行计划。

---

## 场景 A2：用户补充偏好后重排候选

### 给定

已有候选：青岛、杭州、大连、西安。

### 当

用户输入：

```text
更想去海边，最好吃饭方便。
```

### 那么

系统应：

1. 更新 TripBrief themes。
2. 重新评分候选。
3. 提高海边城市权重。
4. 返回更新后的候选卡片。
5. 说明变化原因。

---

## 场景 A3：用户选择目的地

### 给定

DestinationShortlistArtifact 中有青岛候选。

### 当

用户点击“选择青岛”或输入：

```text
那就青岛吧。
```

### 那么

系统应：

1. 调用 `select_destination`。
2. 将 TripBrief.destination 设为青岛。
3. 切换到 Plan Mode。
4. 询问或假设关键缺失信息：抵达/离开时间、是否已定酒店。
5. 不要求用户填写长表单。

---

# B. Plan Mode：自动攻略研究与计划生成

## 场景 B1：用户直接指定目的地

### 给定

用户没有现有 Trip。

### 当

用户输入：

```text
帮我规划青岛 4 天，带父母和两个孩子，节奏轻松一点。
```

### 那么

系统应：

1. 创建 Trip。
2. 识别为 Plan Mode。
3. 更新 TripBrief。
4. 调用 `generate_synthetic_guides`。
5. 调用 `merge_guides`。
6. 调用 `resolve_places_batch`。
7. 调用 `generate_plan`。
8. 调用 `verify_plan_geo`。
9. 返回 PlanArtifact，而不是纯文本攻略。

---

## 场景 B2：缺少抵达离开时间

### 给定

用户说“青岛 4 天”，但没有抵达和离开时间。

### 当

Agent 准备生成计划。

### 那么

系统应：

1. 不阻断计划。
2. 使用明确假设，例如：
   - 第一天午后抵达。
   - 第四天下午离开。
3. 在计划中标注 assumptions。
4. 主动问最多 3 个关键问题。

---

## 场景 B3：用户补充 markdown 攻略

### 给定

Trip 已在 Plan Mode。

### 当

用户粘贴一份 markdown：

```text
# 青岛四天三晚亲子攻略...
```

### 那么

系统应：

1. 调用 `ingest_user_guide_source`。
2. 抽取地点、住宿区域、用餐区域、路线建议、风险。
3. 调用 `merge_guides` 更新 CanonicalGuide。
4. 告诉用户这份攻略带来的变化：新增、强化、冲突。
5. 若已有 PlanArtifact，应询问是否基于新攻略更新计划。

---

## 场景 B4：用户补充小红书链接

### 给定

Trip 已在 Plan Mode。

### 当

用户输入：

```text
这个小红书链接是讲五四广场住宿的：https://...
```

### 那么

系统应：

1. 将链接作为 GuideSource 保存。
2. 尝试读取可用文字或用户备注。
3. 如果无法读取完整内容，不得声称已阅读完整笔记。
4. 可以基于用户备注更新住宿区域判断。
5. 告诉用户该链接处理状态。

---

# C. PlaceFact：地点事实与高德能力

## 场景 C1：核心景点定位

### 给定

CanonicalGuide 中有：八大关、小麦岛、崂山、栈桥。

### 当

系统生成计划前。

### 那么

系统应：

1. 调用 `resolve_places_batch`。
2. 为 4/5 星地点获取 PlaceFact。
3. 保存标准名称、坐标、地址、置信度。
4. 不得让 LLM 自己编写坐标。
5. 在 PlanArtifact 中引用 PlaceFact。

---

## 场景 C2：地点歧义

### 给定

攻略中出现“老街”。

### 当

高德返回多个候选。

### 那么

系统应：

1. 标记 needsReview。
2. 生成 PlaceFactReviewArtifact。
3. 用自然语言问用户：

```text
我找到了几个可能的“老街”，你指的是哪一个？
```

4. 用户确认前，不把该地点作为高置信度核心节点。

---

## 场景 C3：用户询问营业时间

### 给定

用户问：

```text
八大关几点关门？
```

### 当

系统已有或没有 PlaceFact。

### 那么

系统应：

1. 调用 `get_place_detail`。
2. 如果返回营业时间，说明来源和置信度。
3. 如果字段缺失，明确说“当前未获取到可靠营业时间”。
4. 不得由 LLM 猜测。

---

## 场景 C4：打车地址

### 给定

用户在旅行中要去崂山。

### 当

用户输入：

```text
我现在要打车去崂山，打到哪里？
```

### 那么

系统应：

1. 调用 `suggest_taxi_address`。
2. 返回打车地址 / 入口建议 / 高德导航链接。
3. 如果景区入口复杂，提示用户确认入口。
4. 不在 Byway 中自研导航。

---

# D. Plan Artifact：计划生成质量

## 场景 D1：计划必须有用餐锚点

### 给定

用户带老人和孩子旅行 4 天。

### 当

系统生成 PlanArtifact。

### 那么

每个完整游玩日应包含：

1. 午餐区域或餐点建议。
2. 晚餐区域或餐点建议。
3. 如果餐点缺失，PlanWarning 必须提示。
4. activity 不得挤掉 meal anchor。

---

## 场景 D2：抵达日轻量化

### 给定

TripBrief.arrivalInfo = “第一天下午 3 点到”。

### 当

系统生成 Day 1。

### 那么

Day 1 应：

1. 安排抵达、去酒店、放行李。
2. 只安排酒店附近轻活动或晚餐。
3. 不安排远距离重景点。

---

## 场景 D3：离开日轻量化

### 给定

TripBrief.departureInfo = “第四天下午 4 点返程”。

### 当

系统生成 Day 4。

### 那么

Day 4 应：

1. 避免远距离景点。
2. 保留返程缓冲。
3. 用餐区域应靠近酒店/交通方向。

---

## 场景 D4：不明显走回头路

### 给定

计划包含多个分散地点。

### 当

系统调用 `verify_plan_geo`。

### 那么

系统应：

1. 检测明显跨区往返。
2. 生成 geo warning。
3. 给出调整建议。
4. 不承诺导航级最优路线。

---

# E. Travel Mode：旅行中突发事件

## 场景 E1：老人累了 + 晚点

### 给定

Trip 处于 traveling，当前 Day 2，有当前节点和后续节点。

### 当

用户输入：

```text
老人累了，我们晚了 40 分钟。
```

### 那么

系统应：

1. 调用 `get_today_status`。
2. 调用 `record_travel_event`。
3. 调用 `replan_today`。
4. 输出取消 / 顺延 / 重排三类方案。
5. 推荐一个方案。
6. 用户确认前不得调用 `apply_replan`。

---

## 场景 E2：现在大家饿了

### 给定

当前计划下一个是活动，午餐 anchor 即将超时。

### 当

用户输入：

```text
现在大家都饿了。
```

### 那么

系统应：

1. 记录 hungry 事件。
2. 优先保障 meal anchor。
3. 建议暂停或取消低优先级活动。
4. 不建议继续赶景点。

---

## 场景 E3：孩子不想坐车

### 给定

后续计划需要长距离移动。

### 当

用户输入：

```text
孩子不想坐车了。
```

### 那么

系统应：

1. 记录 child_tired 或 transport_problem。
2. 优先推荐附近轻活动 / 回酒店 / 就近用餐。
3. 降级远距离活动。
4. 输出三方案。

---

## 场景 E4：下雨

### 给定

后续有室外活动。

### 当

用户输入：

```text
下雨了，下午怎么安排？
```

### 那么

系统应：

1. 记录 bad_weather。
2. 优先建议室内/低风险替代。
3. 如果没有可靠替代，建议回酒店或用餐区域。
4. 输出调整方案。

---

## 场景 E5：用户拒绝推荐方案

### 给定

Agent 推荐取消小鱼山。

### 当

用户输入：

```text
不，我还是想去小鱼山，取消别的。
```

### 那么

系统应：

1. 理解用户保留小鱼山的偏好。
2. 重新调用 `replan_today` 或更新约束。
3. 给出新的方案。
4. 不强行应用原推荐。

---

# F. Review / Memory

## 场景 F1：每天结束生成日志

### 给定

Day 2 有 TravelEvents 和计划调整。

### 当

用户输入：

```text
今天结束了，帮我总结一下。
```

### 那么

系统应：

1. 调用 `generate_day_log`。
2. 总结原计划与实际完成。
3. 列出取消和调整。
4. 提取潜在 learnings。
5. 保存 DayLogArtifact。

---

## 场景 F2：旅行结束生成总日志

### 给定

Trip 有多个 DayLog。

### 当

用户输入：

```text
这次旅行结束了。
```

### 那么

系统应：

1. 调用 `generate_trip_log`。
2. 总结整体体验。
3. 调用 `extract_family_memory_candidates`。
4. 展示 Memory 候选。
5. 等待用户确认。

---

## 场景 F3：Memory 候选必须确认

### 给定

系统生成 Memory 候选：

```text
父母下午 3 点后不适合高步行活动。
```

### 当

用户未点击接受。

### 那么

该 Memory：

1. 状态为 candidate。
2. 不参与后续 Dream/Plan。
3. 不写入 accepted memory。

当用户点击接受后：

1. 调用 `accept_family_memory`。
2. 状态变为 accepted。
3. 后续推荐和计划可以使用。

---

# G. 边界场景

## 场景 G1：用户要求订酒店

### 当

用户输入：

```text
帮我直接订五四广场附近的酒店。
```

### 那么

系统应：

1. 明确说明 Byway 不负责预订和支付。
2. 推荐住宿区域和选择标准。
3. 用户自行去携程/飞猪等平台预订。
4. 用户订好后可以把酒店名称/地址发给 Byway。

---

## 场景 G2：用户要求真实小红书评论

### 当

用户输入：

```text
帮我抓一下这个小红书下面所有评论。
```

### 那么

系统应：

1. 不做评论抓取承诺。
2. 如果用户提供截图或文案，可以总结其中内容。
3. 说明只能基于用户提供内容或可访问公开内容。

---

## 场景 G3：高德 API 失败

### 给定

`resolve_places_batch` 调用高德失败。

### 当

系统需要生成计划。

### 那么

系统应：

1. 返回可恢复错误。
2. 说明地点事实未完全确认。
3. 可以生成低置信度草案。
4. 标记核心地点需要复核。
5. 不得伪造坐标或路线。

---

## 场景 G4：用户刷新页面

### 给定

Trip 正在 Travel Mode，已有 TodayArtifact。

### 当

用户刷新网页。

### 那么

前端应：

1. 调用 `GET /api/trips/:tripId`。
2. 调用 `GET /api/trips/:tripId/artifacts`。
3. 恢复当前 Day、当前节点、下一个节点和 pending confirmations。

---

## 场景 G5：Agent 不应过度追问

### 当

用户输入：

```text
帮我规划杭州 3 天，夫妻两人带 12 岁孩子，轻松一点。
```

### 那么

Agent 不应一次性问 10 个问题。它应：

1. 基于合理假设生成草案。
2. 最多追问 3 个会显著影响计划的问题。
3. 明确列出假设。

---

# H. 验收成功标准

完成实现后，至少应满足：

1. 能从自然语言进入 Dream / Plan / Travel / Review。
2. 能生成结构化 Artifact。
3. 能调用 PlaceFact 工具定位核心地点。
4. 能处理旅行中事件并输出三方案。
5. 能保存和恢复 Trip 状态。
6. 能生成 DayLog / TripLog / Memory Candidate。
7. 不做 OTA、不爬小红书评论、不编造事实。
